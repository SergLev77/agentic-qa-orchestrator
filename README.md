# Agentic QA Orchestrator

Thin main agent + zone subagents for QA work. Measurable context savings, eval and routing audit.

> Personal project. Generic engineering pattern only: no employer data, internal
> systems, schemas, hosts or credentials. Names, domains and identifiers are
> masked or replaced with neutral examples.

Эта работа о том, как перестроить AI-агента для QA так, чтобы он не сжигал контекст на каждом шаге, не терял возможности действовать и при этом **измеримо** не терял в качестве.

Всё ниже проверено на реальной рабочей конфигурации: замеры, eval и аудит маршрутизации сняты по логам сессий, а не «на глаз».

## Проблема

Типичный AI-агент для QA подключает все интеграции сразу: трекер, база знаний, git-хостинг, тест-менеджмент, kubernetes, чат, автоматизация. Каждый MCP-сервер добавляет десятки JSON-схем инструментов, и эти схемы попадают в контекст **на каждом шаге**.

Последствия:

- базовый контекст шага раздувается до десятков тысяч токенов ещё до первого слова пользователя;
- каждая сессия дороже, быстрее упираемся в компакцию;
- в длинных сессиях модель «теряет середину»;
- у главного агента сосредоточены опасные инструменты (удаление, кредиты/секреты), которые там не нужны.

## Решение: тонкий оркестратор + зоны

Главный агент (`main`) не видит ни одного MCP. Он умеет:

- `bash` (SQL, CLI git-хостинга, скрипты, `git`);
- `edit`, `webfetch`;
- `task` (делегирование субагентам).

Тяжёлое уходит в **зоновые субагенты** с узким allowlist: у каждого внешнего сервера ровно один владелец.

```
main (bash, edit, webfetch, task — без MCP)
 ├── research      → tracker + wiki            (read-only)
 ├── code          → git hosting via CLI       (read-only)
 ├── knowledge     → files, DB schema, logs    (read-only)
 ├── infra         → k8s scripts               (mutations only after explicit approval)
 ├── testcases     → case writer + reviewer    (reviewer is independent)
 ├── chat          → chat MCP                  (read L1, send L3)
 └── automation    → automation MCP            (read L1, write L3)
```

Принципы, которые всё держат:

- **Least privilege.** MCP-инструмент живёт только в своей зоне.
- **Human-gates.** Запись, внешние сообщения, merge request, прод — только после явного «да».
- **Verification before trust.** Результат субагента проверяется фактом или независимым ревьюером.
- **Hybrid, not extremes.** Прямое действие там, где дешевле; делегирование там, где нужен узкий доступ.

## Результат (измерено)

| Метрика | Широкий main | Тонкий main | Изменение |
|---|---:|---:|---|
| `total` первого шага | 35530 | 18003 | **−49%** |
| `cache_read` | 32768 | 16384 | −50% |

Метод замера: первая ступень главной сессии, `parent_id IS NULL`, ≥5 шагов, одинаковая модель, сопоставимая задача. На длинной истории широкого агента значения держались в диапазоне ~34-40k.

### Качество не просело

- Eval-банк из 12 вопросов по 6 категориям (контекст, тест-менеджмент, SQL, логи, стенды, домен): **12/12 PASS**.
- Критерий PASS: ожидаемый факт **и** ссылка на источник. Ответ без источника считается FAIL.

### Маршрутизация проверена по логам

Пять задач в живых сессиях, аудит по базе вызовов инструментов:

| Проверка | Ожидание | Факт | Итог |
|---|---|---|---|
| Tracker/wiki | делегировать | 1 task → research | PASS |
| Merge request | делегировать | 1 task → code | PASS |
| SQL-запрос | **сам** через bash | 1 вызов, без task | PASS |
| Chat | делегировать, без отправки | 1 task, write = 0 | PASS |
| Automation | делегировать, read-only | 1 task, write = 0 | PASS |

Ключевой момент: агент не «делегирует всё подряд» и не «делает всё сам». SQL он выполняет напрямую, а tracker отдаёт зоне.

## Что забираю из этого как инженер

1. **Контекст это бюджет.** Схемы инструментов стоят токенов на каждом шаге; один `bash` дешевле пятидесяти MCP-инструментов.
2. **Измерять, а не верить.** Baseline, eval и аудит вызовов превращают «кажется, стало лучше» в цифры.
3. **Права это архитектура, а не настройка.** Правильный allowlist по зонам и human-gates — часть дизайна.
4. **Гибрид лучше крайностей.** Прямое действие там, где дешевле, делегирование там, где нужен узкий доступ.

## Ограничения и честные оговорки

- Замеры сняты на одной модели и одном наборе задач; это инженерный контроль изменения, не бенчмарк.
- Eval прогонялся на файловой базе знаний, без внешних MCP.
- Экономия зависит от числа MCP-инструментов в исходной конфигурации: чем больше серверов, тем больше выигрыш.
- Названия и данные внутренних систем из этого репозитория удалены или заменены на обобщённые.
