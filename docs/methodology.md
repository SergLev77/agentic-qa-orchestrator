# Methodology: как измерять агента, а не верить ему

Три независимых измерения. Вместе они отвечают на вопрос «стало ли лучше», не давая подменить ощущениями.

## 1. Baseline контекста

Что мерим: сколько токенов уходит на **первый шаг** главной сессии. Именно там лежат инструкции и схемы инструментов, поэтому это честная цена конфигурации.

Правила:

- главная сессия: `parent_id IS NULL`;
- минимум 5 шагов (короткие сессии нерепрезентативны);
- метрика — `tokens.total` и отдельно `tokens.cache.read`;
- `input` без кэша нестабилен: при прогретом кэше он почти ноль, вес уходит в `cache.read`;
- сравнивать можно только при одинаковом наборе инструментов главного агента: схемы входят в первый шаг;
- замеры «ответь одним словом» недействительны.

См. `examples/measure-baseline.sql`.

## 2. Eval качества

Банк вопросов с эталонными ответами и обязательными источниками.

- 12 вопросов, 6 категорий, по 2 на категорию;
- PASS только если есть **и** ожидаемый факт, **и** ссылка на источник;
- порог: ≥10/12 и хотя бы один PASS в каждой категории;
- банк вопросов попадает агенту, ключ с ответами — нет.

Так измеряется, не деградировал ли агент после оптимизации контекста.

## 3. Аудит маршрутизации

Проверка «сам vs делегируй» по фактам, а не по описанию.

Для каждой задачи в логах смотрим:

- под каким агентом шла сессия;
- был ли вызов делегирования и с каким адресатом;
- были ли запрещённые прямые вызовы (MCP в main, write-действия).

Проверки строятся так, чтобы у задачи был ровно один правильный путь: одна должна делегировать, другая **не должна** (прямой SQL через bash). Это ловит и «всё делает сам», и «всё делегирует».

## Как читать результат

- Baseline упал, eval не упал, routing зелёный — оптимизация удалась.
- Baseline упал, eval упал — сэкономили на знаниях, откатывать.
- Baseline упал, routing зелёный, но задачи стали медленнее — проверить, не делегируется ли мелочь.
